# Masta-OCTA / OCTA-node 実装計画書

**Octatrack Performance System - Architecture & Implementation Plan**  
Version 0.1 / 2026-09-06  
Status: Architecture Baseline Draft  
対象: Masta-OCTA M5完了後の開発基準

---

## 0. エグゼクティブサマリー

Masta-OCTAは、単なるOctatrackのファイル管理アプリや汎用DAWへ進めない。最終形は、**Octatrack MKIIを中心としたPerformance SystemのControl Plane**とする。

リアルタイムAudio/MIDI処理はRaspberry Piベースの外部機器 **OCTA-node** に分離する。Octatrackは演奏・シーケンス・サンプリングの中心、OCTA-nodeはAudio routing / 4ch Looper / DSP / Recording / MIDI Clock、Masta-OCTAはLibrary / Project / Session / Routing / Visualization / Node Controlを担当する。

現行M5で進めているFAT hash、rename planning、apply、restart continuation、Gate C、安全なPlan -> Review -> Apply -> Verifyの思想は捨てない。むしろ、今後のSample編集、Routing変更、Node設定、Session適用にも共通する基本原則へ格上げする。

直近の優先順位は次の通り。

1. M5 / Gate Cを完遂し、現在の安全境界を固定する。
2. Library UIを再構築し、ファイルブラウズとSample Inspectorを主役にする。
3. AudioAsset / PerformanceSession / Transport / Routing / NodeCapabilityのDomain境界を導入する。
4. Waveform v2とAudio Analysis Pipelineを作る。
5. NodeClient + MockNodeでOCTA-node不在でもPerformance UIを開発できるようにする。
6. OCTA-node prototypeを4 IN / 8 OUT、4 Loop Engine、MIDI同期から開始する。
7. Masta-OCTA + OCTA-node + Octatrack MKIIを一つのPerformance Systemとして統合する。

## 1. プロダクト定義

### 1.1 現在

Masta-OCTAは、OctatrackのSet / Project / Audio Pool / Sampleを安全に扱う管理アプリとして発展している。現在の重要な資産は以下。

- Octatrack root / Set / Projectの探索と管理
- Audio Pool / Sample browser
- Sample metadata / note / tag
- waveform解析・preview
- read-only sourceとdisposable cloneを分離する安全設計
- rename planning / applyの境界
- hash再確認、destination collision検査、同一directory制約
- restart / tamper / double-applyを意識したGate C系の安全設計
- 実機メディアを直接壊さない運用思想

### 1.2 目標

Masta-OCTAを次の定義へ拡張する。

> **Masta-OCTA = Octatrack Performance SystemのControl Plane**

汎用DAWとの競争は目的にしない。Ableton LiveやLogicの代用品ではなく、Octatrackの弱点をPCと専用Nodeで補い、実機の演奏性を拡張する。

### 1.3 最終構成

```text
┌────────────────────────────────────────────┐
│                Masta-OCTA                  │
│                                            │
│ Library / Project / Performance            │
│ Waveform / Routing / Automation            │
│ Session / Node Control                     │
│                                            │
│              CONTROL PLANE                 │
└──────────────────┬─────────────────────────┘
                   │
          OCTA-node Protocol
        Ethernet / USB / Local API
                   │
┌──────────────────▼─────────────────────────┐
│                OCTA-node                   │
│                                            │
│ Audio Engine / 4x Looper / Router          │
│ DSP / Recorder / MIDI Clock / Recovery     │
│                                            │
│              REALTIME PLANE                │
└──────────────────┬─────────────────────────┘
                   │
             AUDIO / MIDI
                   │
┌──────────────────▼─────────────────────────┐
│             OCTATRACK MKII                 │

└────────────────────────────────────────────┘
```

### 1.4 各レイヤーの責務

| レイヤー | 主責務 | やらないこと |
|---|---|---|
| Masta-OCTA | Library、Project編集、可視化、Session、Routing指示、Node制御 | realtime audioを演奏の必須経路にしない |
| OCTA-node | Audio I/O、Looper、DSP、routing、recording、MIDI clock | 重いLibrary UI、AI解析を常時抱えない |
| Octatrack MKII | 演奏、sequencer、sampler、scene、実機操作 | PC的な大規模ファイル管理・解析 |

## 2. 最上位設計原則

### 2.1 Octatrackを置き換えない

Masta-OCTA / OCTA-nodeはOctatrackの代替ではなく拡張である。Octatrack本体が得意な演奏、Pattern、Scene、Samplingを尊重し、外部で以下を補う。

- 大画面のSample探索
- waveform詳細表示
- 非破壊編集・解析
- 4ch quantized looper
- 追加Audio outputs
- External FX routing
- recording / resampling
- stem / transient / slice preparation
- Session単位の再現

### 2.2 PCが落ちても音を止めない

Masta-OCTA crash、Mac sleep、Network断が起きても、OctatrackとOCTA-nodeは演奏継続できることを要求する。Realtime audio threadとUI/APIを分離し、MacをClock必須経路に置かない。

### 2.3 非破壊を標準にする

Original sampleは原則変更しない。trim、stem、slice、normalize、recording等は派生AudioAssetとして管理する。元ファイルとの系譜、hash、処理条件を追跡できるようにする。

### 2.4 Intent -> Plan -> Review -> Apply -> Verify

現行M5の安全思想を全体へ展開する。

```text
Intent
  ↓
Plan
  ↓
Review
  ↓
Apply
  ↓
Verify
```

対象はfile renameだけでなく、copy、move、routing変更、Node設定、Session recall、Octatrack向けexportにも適用する。

### 2.5 Capability-driven

Masta-OCTAがOCTA-nodeのhardware versionを直接判定しない。Nodeがcapabilityを返し、UIとcommand availabilityを構成する。

## 3. 現行M5の扱い

### 3.1 方針

M5 / Gate Cは中断・破棄しない。現在の安全境界を完成させてから、次のArchitectureへ進む。

### 3.2 M5で固定すべき資産

- read-only sourceとwrite対象の明確な分離
- disposable cloneによる安全なwrite検証
- source / destinationのhash確認
- rename planning facts
- destination collisionの検査
- tamper検知
- double-apply防止
- restart continuation
- Human Gate C
- apply後verify

### 3.3 M5完了条件

- Gate Cの必須試験が再現可能な手順として固定されている
- FAT/hash safetyが実機メディア上でも破綻しないことを確認している
- restart / tamper / double-applyの期待結果が文書化されている
- rename操作が「UIの都合」ではなく安全なdomain operationとして切り出されている
- M6以降がM5の安全境界を迂回しない

## 7. Waveform v2 / Audio Analysis Pipeline

### 7.1 現状課題

現行waveformは固定640 points表示を前提とし、表示幅を広げても情報量が増えない。解析側も基本解像度が粗く、stereoが1本へ潰れるため、Sample EditorやLooper Editorへ進むには不足する。

### 7.2 Waveform v2要件

最低限以下を扱う。

- range start / end
- requested width / resolution
- zoom
- scroll
- stereo channel separation
- min/max peak representation
- selection range
- deterministic cache key

将来追加:

- transient marker
- slice marker
- loop point
- trim
- fade

### 7.3 Analysis Pipeline

```text
AudioAsset
   ↓
Decode / Probe
   ↓
Waveform Pyramid
   ↓
Transient Analysis
   ↓
Tempo / basic feature analysis
   ↓
Optional Stem Separation
   ↓
Derived AudioAssets
```

解析処理は非同期・非破壊とし、Library browsingやpreviewをblockしない。

## 8. Stem Separation

### 8.1 目的

完成済みloopやsampleをOctatrackで再構成しやすい素材へ分解する。

ターゲット例:

- KICK
- SNARE
- HI-HAT
- BASS
- MELODY / OTHER
- VOCAL（必要時）

完全分離を保証しない。精度差を前提に、人間がpreviewして採用するworkflowにする。

### 8.2 推奨pipeline

```text
Original Sample
      ↓
Stage 1: broad source separation
      ├ DRUMS
      ├ BASS
      ├ VOCAL
      └ OTHER / MELODY

DRUMS
      ↓
Stage 2: drum separation
      ├ KICK
      ├ SNARE
      ├ HI-HAT
      └ PERC / OTHER
```

modelは交換可能なadapter境界に置き、特定AI modelへdomainを依存させない。

### 8.3 派生Asset

```text
DRUM_BREAK.wav
├ original
├ stem:kick
├ stem:snare
├ stem:hihat
├ stem:bass
└ stem:melody
```

metadata例:

```text
derivedFrom = DRUM_BREAK.wav
process = STEM_SEPARATION
model = <adapter/model version>
stem = KICK
confidence = optional
```

### 8.4 実行場所

Stem separationは原則 **Masta-OCTA / Mac側** で行う。OCTA-nodeはRealtime audioを優先し、重いAI inferenceを演奏中の必須処理にしない。

## 9. OCTA-node プロダクト定義

OCTA-nodeはRaspberry PiベースのOctatrack realtime expansion / audio bridge。

疑似Overbridge的な体験を提供するが、Octatrack内部8track busへ直接アクセスする装置ではない。公開されたphysical Audio / MIDI I/Oを使う。

主機能:

- Octatrack MAIN / CUE capture
- MAIN / CUE hardware thru
- 4 Loop Engines
- 8ch output routing
- external input / return
- MIDI Clock / Transport
- realtime DSP
- recording / resampling
- Masta-OCTA remote control
- crash/restart recovery

---

## 10. OCTA-node Hardware Architecture

### 10.1 I/O方針

最終目標は **8 IN / 8 OUT**。

ただし最初のprototypeは **4 IN / 8 OUT** でも成立する。Software architectureは最初から8x8を表現できるようにする。

### 10.2 Output割当の標準

| Physical Output | Default role |
|---|---|
| OUT 1/2 | OCTATRACK MAIN THRU |
| OUT 3/4 | OCTATRACK CUE THRU |
| OUT 5/6 | NODE OUT 1 |
| OUT 7/8 | NODE OUT 2 |

内部は8 mono busesとして扱い、UIでは8 MONO / 4 STEREO / CUSTOMを選べる。

### 10.3 Input標準

初期4 IN:

| Input | Role |
|---|---|
| IN 1/2 | Octatrack MAIN tap |
| IN 3/4 | Octatrack CUE tap |

8 IN版ではIN 5/6、7/8をexternal synth / FX return等に利用する。

### 10.4 Hardware Thru / Bypass

MAIN/CUEはPi DSPを必須経路にしない。

```text
                  ┌─ Analog / Relay Thru ─→ OUTPUT
Octatrack MAIN ───┤
                  └─ ADC TAP ─────────────→ Node DSP
```

Node process停止、OS再起動、network断でもMAIN/CUEを通す設計を優先する。

### 10.5 Compute / Storage

初期候補:

- Raspberry Pi 5
- class-compliant multi-channel Audio I/Fまたは専用codec構成
- MIDI IN / OUT
- NVMe storage
- optional small display
- optional physical REC / MUTE / SHIFT / UNDO controls

具体的Audio I/Fはprototype前にlatency、Linux driver安定性、multi-output、power要件で比較する。

## 11. OCTA-node Looper

### 11.1 基本モデル

4 independent Loop Engines。

```text
LOOP 1
LOOP 2
LOOP 3
LOOP 4
```

運用mode:

- 4 mono
- 2 stereo
- custom assignment

### 11.2 必須機能

- ARM / REC
- PLAY
- STOP
- OVERDUB
- UNDO
- MUTE
- CLEAR
- REVERSE
- HALF SPEED
- DOUBLE SPEED
- LEVEL
- PAN

### 11.3 Quantized Record

Octatrack MIDI Clockを基本masterとする。

```text
REC ARM
  ↓
次のquantize boundaryまで待機
  ↓
RECORD
  ↓
1 / 2 / 4 / 8 / 16 / 32 bars
  ↓
自動STOP
  ↓
PLAY
```

### 11.4 CUE -> Looper

主要な演奏workflow。

```text
Octatrack Track
     ↓ CUE
OCTA-node Capture
     ↓
Looper
     ↓
Reverse / Half / Filter / Delay
     ↓
NODE OUT
```

これによりOctatrackのCUEを外部Flex/Looper sendのように扱える。

### 11.5 Scene連携

将来はOctatrack crossfader / scene情報とNode側Sceneを連動させる。

例:

```text
Scene A: Loop1 100%, Loop2 0%, FX low
Scene B: Loop1 0%, Loop2 100%, Delay high
```

## 13. Overbridge-like Integration と限界

### 13.1 提供したい体験

- Octatrack MAIN/CUEをNode経由でcapture
- Masta-OCTAからMixer / Routing / Looperを制御
- Macへ複数Audio channelsを提供する構成を検討
- MIDI clock / transport / remote control
- Sample / Project / Recordingの統合管理

### 13.2 明確な限界

Octatrack本体の内部8 audio tracksをそのまま独立8ch realtime streamとして取得することは前提にしない。Physical MAIN/CUEとMIDIで成立する機能に限定する。

### 13.3 Automated Stem Export

Octatrack trackのSolo/Mute、transport、recordingを利用し、複数passでstemを書き出す機能を将来実装する。

```text
T1 SOLO → record → T1.wav
T2 SOLO → record → T2.wav
...
T8 SOLO → record → T8.wav
```

これはrealtime 8ch Overbridgeではなく、**automated offline/realtime-pass export**として明示する。Random LFO、probability、external input等によりpass間が一致しない可能性も表示する。

## 14. Masta-OCTA <-> OCTA-node Protocol

### 14.1 NodeClient abstraction

Masta-OCTAのUI/domainがtransport実装へ直接依存しないようにする。

```text
NodeClient
├ getStatus()
├ getCapabilities()
├ getRouting()
├ planRoutingChange()
├ applyRoutingChange()
├ setTempo()
├ setScene()
├ armLooper()
├ recordLooper()
├ stopLooper()
├ clearLooper()
└ saveSession()
```

### 14.2 MockNode

実機完成前はMockNodeを用意する。

```text
Masta-OCTA
    ↓
NodeClient
   ├ MockNode      ← M8までの主要開発
   └ NetworkNode   ← hardware接続後
```

### 14.3 Protocol要件

- command / response ID
- idempotency where applicable
- monotonic state revision
- capability negotiation
- event stream
- reconnect後のfull state reconciliation
- transport切断時にRealtime Engineを停止しない
- destructive commandのplan/review boundary

Transport方式はNode prototype前にADRで決定する。Ethernetを第一候補とし、USBはAudio device / maintenance / direct linkの役割を分けて評価する。

## 16. Recording / Storage / Recovery

### 16.1 Buffering

LooperはRAM中心に保持する。

```text
Audio Interface
      ↓
Realtime Ring Buffer
      ↓
Loop RAM Buffer
   ├→ Playback
   └→ Background persistence
              ↓
             NVMe
```

SD cardへRealtime threadから同期書き込みしない。

### 16.2 Recovery

対象障害:

- Masta-OCTA disconnect
- Node API process restart
- Audio engine process crash
- OS restart
- power loss

Loop audio、session metadata、routing stateのrecovery戦略を段階的に導入する。

V1の最低要件は、Masta-OCTA切断で音が止まらないこと。V1.1以降でprocess restart / power recoveryの保証レベルを上げる。

## 25. 結論

Masta-OCTAの進化方向は「DAW化」ではなく、**Octatrackを中心にした専用Performance System化**とする。

Masta-OCTAは頭脳、OCTA-nodeはRealtime audio / MIDIの実行層、Octatrack MKIIは演奏機。この3層を明確に分けることで、現在のファイル安全設計、Library UI、Waveform v2、Stem Separation、4ch Looper、8out Routingが矛盾せず一本の開発線につながる。

最優先はM5完了。その後、M6 Library Workspaceから画面構造を整理し、M7 Audio Analysis、M8 MockNode、M9 Hardware、M10 Integrationの順で進める。

この文書を、今後のMasta-OCTA開発におけるArchitecture / Scope / Milestoneの基準文書とする。
